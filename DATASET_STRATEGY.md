# LayerNet dataset strategy

**Decision date:** 2026-10-04
**Scope:** Dataset selection and leakage-aware evaluation design. PaySim source/access and causal customer-recipient sequence feasibility are verified; no PaySim model has been trained.

## FCA APP go/no-go verification

**Decision: NO-GO for immediate LayerNet integration or model experiments.** FCA APP remains a promising candidate, but the public official materials do not let us verify the exact release schema or the applicable data-use terms needed for this FYP. This is an evidence/access gate, not a finding that the dataset is unsuitable in principle.

### Verified source and version evidence

- The FCA's current APP dataset overview says the asset is accessed through the FCA Innovation platform. It describes 37 datasets, 15 million transactions, 58 million data points, 61,000 attempted fraud events, a two-year period, and approximately 20,000 synthetic individuals. The page identifies synthetic individual/business identities, bank-account details, call/SMS metadata, and reported/successful fraud instances. Its page date is 5 December 2025, but the public page gives no release/version identifier or file manifest. [FCA APP overview](https://www.fca.org.uk/firms/digital-sandbox/authorised-push-payment-synthetic-data)
- FCA's Digital Sandbox access page requires platform signup and an application/eligibility assessment for the Permanent Digital Sandbox. It explicitly invites academic institutions to apply to conduct research projects, which supports an academic route but is not a blanket FYP license or confirmation that an individual student can obtain this dataset. [Digital Sandbox application and eligibility](https://www.fca.org.uk/firms/innovation/digital-sandbox)
- FCA's 31 December 2024 evaluation report documents updates through July 2024 (including transaction-category/currency and date/time formatting changes) and an expanded profile release in November 2024. It recommends that FCA provide a more detailed schema, data dictionary, and samples. The report also records that users wanted offline access but understood they could not simply take the data and work offline. The 2024 report is not proof of current terms, so the 2025 platform release's terms still need to be obtained. [FCA-commissioned dataset evaluation](https://www.fca.org.uk/publication/external-research/app-fraud-dataset-evaluation-report.pdf)
- FCA's synthetic-data report confirms the conceptual data model: synthetic identity/account/transaction tables; payments trackable between account holders across banks; call/SMS metadata; and ground truth for attempted and successful scams identifying scammer and victim. It states the data was produced by agent-based simulation over two years and represented to participants as flat files aligned with banking/telco schemas. This verifies the broad capabilities, not the exact columns in the current release. [FCA report on synthetic data](https://www.fca.org.uk/publication/corporate/report-using-synthetic-data-in-financial-services.pdf)

This evidence suggests FCA APP could support a synthetic APP-scam sequence study if admitted to the platform and if the delivered schema exposes usable keys/times/labels. It does not yet support an implementation decision: the actual fields, their semantics, and permitted research workflow remain unverified. Because the release is synthetic and APP-scam focused, even a later GO would support only that stated research domain, not claims about real card fraud.

### Fallback check: PaySim, then IEEE-CIS

PaySim's author-attributed Kaggle release is now verified as Version 2 with a CC BY-SA 4.0 license. The local archive's SHA-256 is `f7eef9ffad5cfa64a034143a5c9b30491d189420b273d5ad5723ca40b596613d`; the archived CSV was schema- and row-audited. The release contains 6,362,620 rows and hourly steps 1–743. This clears the access gate for the scoped synthetic-data research use subject to attribution and ShareAlike obligations. It supports recipient histories for `nameDest` values beginning with `C`, but not a meaningful sender-personalized study: repeated `nameOrig` history was sparse in the verified release. The history/sequence report is generated by `ml/src/layernet_ml/paysim_data.py` and recorded at `ml/reports/paysim-sequence-contract-v1.json`. [Original PaySim paper](https://www.msc-les.org/proceedings/emss/emss2016/emss2016_249.html) · [Author's Kaggle dataset page](https://www.kaggle.com/datasets/ealaxi/paysim1) · [CC BY-SA 4.0 terms](https://creativecommons.org/licenses/by-sa/4.0/)

IEEE-CIS is the next candidate with an inspectable official schema and explicit academic-use permission: Kaggle lists transaction/identity files, `TransactionID` joins, `isFraud`, relative `TransactionDT`, amount, card/address/product fields, and device identity columns. Its rules allow non-commercial academic research and education but prohibit redistribution. Its schema does **not** document a person/account key; `card1`–`card6` are card attributes, and identity/device fields are missing for many transactions. It can support a separate chronological card-attribute/device-context benchmark, not personalized customer baselines. [Official IEEE-CIS data page](https://www.kaggle.com/competitions/ieee-fraud-detection/data) · [Official competition rules](https://www.kaggle.com/competitions/ieee-fraud-detection/rules)

PaySim is now feasible for a **narrowed synthetic customer-recipient temporal study**, while IEEE-CIS remains an option for a separate card/device/context benchmark. Neither supports claims about real-world personalized fraud behavior. FCA APP remains gated by its current data dictionary and data-use terms.

## Current pipeline and ULB/Worldline limits

The existing `ml/` pipeline is a ULB/Worldline binary-classification baseline. It expects `Time`, `Amount`, `V1`–`V28`, and `Class`; uses `log1p(Amount)`, cyclic elapsed-time features, and the PCA components; and creates chronological 60/20/20 splits with tied times kept together. The model-training command is an XGBoost baseline, but the raw CSV is not bundled. No trained artifact or result is claimed.

The dataset has 284,807 transactions from two days in September 2013, including 492 frauds (0.172%). Its visible fields are elapsed seconds, amount, 28 identity-protecting PCA components, and the binary fraud label. It is useful for a conventional, highly imbalanced fraud benchmark and a chronological evaluation. It has no account/customer identifier, transaction type, device, merchant, location, or channel field. `Time` orders the overall file but cannot form user histories. Therefore it cannot validate account-level behavior, personal baselines, device/location/channel changes, or user-sequence models. The PCA fields also do not provide human-readable evidence. BERD identifies Worldline and ULB as the creators and points to Kaggle for full access; its record does not itself state a dataset license, so retain Kaggle's current terms with any research copy. [BERD dataset record](https://berd-platform.de/records/qcqqe-g6q16) · [Kaggle source](https://www.kaggle.com/datasets/mlg-ulb/creditcardfraud)

## Experimental strategy

### A. Traditional fraud benchmark

Keep ULB/Worldline as the first supervised benchmark for the current XGBoost pipeline and later comparable traditional baselines. Report it only as performance on this two-day anonymized card dataset. Use fraud-sensitive metrics (especially average precision / PR-AUC, recall and precision at a threshold selected on validation) and disclose the extreme base rate. Do not interpret uncalibrated model scores as probabilities.

### B. Behavioral and sequence research

FCA APP remains the best conceptual match, but its current decision is **NO-GO** pending a current field dictionary and written data-use terms. PaySim supports a verified, synthetic customer-recipient history study using `nameDest` values beginning with `C`; it must not be described as sender-personalized or real-customer behavior. IEEE-CIS remains a separate card-attribute/device-context temporal track after accepting its academic-use terms. The Handbook simulator remains an alternative after its data license is clarified.

### C. Experiment-to-dataset mapping

- ULB: amount/time/PCA supervised benchmark and chronological XGBoost baseline.
- FCA APP (preferred, gated): per-person/account behavioral baselines, causal transaction-history features, and temporal sequence experiments for APP fraud labels.
- PaySim: per-recipient causal transaction history and sequence experiments using amount, transaction type, and hourly gaps; no source-person personalization, device, geographic location, or channel claims.
- IEEE-CIS (optional separate track): conventional supervised benchmark and exploratory card-field/device-context analysis, with identity missingness reported. No customer-level claims.
- Handbook simulator (optional methodology track): controlled, reproducible tests of known customer/terminal/time fraud scenarios only after license review.

### D. Leakage-resistant evaluation

1. Validate the source release and its data dictionary first; record source URL, terms/license, file hashes, row counts, label meaning, time range, identifier coverage, and missingness. Never infer unsupported identity or location semantics from coded fields.
2. Split chronologically on the transaction/event timestamp into contiguous train, validation, and final test windows. Keep equal-time groups together. Fit imputers, encoders, scaling, feature selection, calibration, and thresholds using training/validation only as appropriate; freeze them before the final test.
3. Build account/customer history features causally: for an event at time *t*, use only that entity's events strictly before *t*. Do not use target labels, future aggregates, future balance state, `isFlaggedFraud`, or fraud-rate features computed with labels from validation/test. Any delayed-label feature must model the real label-availability delay and be tested separately.
4. Use validation for model selection and decision-threshold/calibration selection. Evaluate the final test once. Report split dates, class counts, unseen-entity proportions, identity/device coverage, and PR-AUC plus operational threshold metrics. Do not randomly oversample before splitting; if sampling is studied, apply it to training only.
5. For cold-start generalization, add a separately declared entity-disjoint test experiment; it answers a different question from future transactions for known entities and does not replace the chronological test.

### E. Keep datasets separate

Do **not** concatenate ULB, PaySim, IEEE-CIS, FCA APP, or Handbook rows into one training table or one headline score. They differ in transaction domain, identity semantics, time encoding, feature schema, label-generation process, and synthetic/real status. Maintain versioned dataset-specific schemas and feature adapters; compare results side by side with clear scope. Cross-dataset transfer can be a later, explicitly defined experiment after compatible labels/features and terms are established.

## PaySim sequence feasibility status

Phase 10's dataset report is at `ml/reports/paysim-sequence-contract-v1.json`. It pins the author release hash and the split steps (train 1–281, validation 282–355, test 356–743). Its sequence contract groups simultaneous same-hour events, permits only strictly earlier steps as history, allows validation/test targets to use earlier partition context, excludes labels/rule flags/balances/entity IDs from model inputs, and derives the maximum history length from training targets only. The 95th-percentile cap is 17 distinct prior step buckets; truncation keeps the most recent whole buckets. This establishes a dataset/sequence contract only: no temporal model has been designed or trained, and the supported entity is recipient-side `nameDest` only.

Run or regenerate the Phase 10 report with `ml/.venv/Scripts/python -m layernet_ml.cli validate-paysim-sequences --archive ml/data/paysim/paysim-author-release-v2.zip --output ml/reports/paysim-sequence-contract-v1.json`. Phase 11 adds `iter_paysim_archive_sequences`, a chunked lazy loader that consumes that report and retains no expanded sequence artifact. The `materialize-paysim-sequences` command streams all recipient examples to verify counts against Phase 10 and writes a compact reproducibility manifest. It does not train a model. The next research phase is the temporal-model experiment using this loader, with leakage-safe chronological evaluation.
