@CHAPTER 1|INTRODUCTION

## 1.1 Introduction
Digital payments have become part of ordinary life. Card payments, mobile wallets, online banking and merchant point-of-sale terminals move a very large number of small transactions every day. Each of these channels can be abused. Stolen card details, account takeover, mule accounts and money transfers that are later reversed all appear in transaction data as records that look almost normal. Fraud analysts therefore face two related problems: finding the few suspicious records among very many legitimate ones, and explaining why a record deserves attention so that a human can act on it {bolton} {abdallah}.

LayerNet is a final year project that addresses this problem from two directions. The first is a working web application, the **LayerNet investigation dashboard**, built with Next.js, React and TypeScript {nextjs} {react}. An analyst can enter a transaction, receive a transparent priority score from a rules-based baseline, see every point that contributed to that score, save the record, and review saved records on a dashboard, a searchable history and an analytics page. The second is an **offline machine-learning research track** in Python. It trains and evaluates tree-based models on the public ULB/Worldline credit-card dataset {dalpozzolo15} {ulbkaggle} and studies whether the recent history of a payment recipient adds useful signal on the synthetic PaySim mobile-money dataset {paysim}.

The two parts are deliberately kept separate. The live Analysis page uses only the rules baseline, which produces an uncalibrated priority score between 0 and 100. It is not a fraud probability and it is not the output of a trained model. Trained XGBoost and Random Forest models are exposed only through a separate Benchmark page, which scores uploaded rows in the ULB format on the server and labels the results as dataset-scoped benchmark inference. This separation is a design decision of the project: it keeps every number on the screen honest about where it came from.

This report covers Chapters 1 to 4 of the NUML final year project format: the introduction, background and existing work, requirements specification, and system modelling, followed by appendices. Implemented, partial, experimental and planned items are named as such throughout.

## 1.2 Motivation
Three observations motivated the project. First, many student and tutorial fraud-detection projects present a single accuracy figure on a highly imbalanced dataset. When fraud is well below one percent of all transactions, accuracy is dominated by the legitimate class and says little about how well fraud is found {saito} {davis}. A useful project should report metrics that reflect the minority class, such as Average Precision and precision-recall curves, and should be clear about how thresholds were chosen.

Second, a model score alone is rarely enough for an investigator. Analysts need to see which inputs pushed a case upward, what the system cannot see, and what a sensible next action is. Even a simple rules engine is valuable when it is transparent and its limits are visible, and it provides a baseline against which learned models can later be compared.

Third, history matters in fraud. Earlier work shows that aggregating a card's or customer's past transactions can improve detection {whitrow} {bahnsen} and that sequence models can learn from transaction order {jurgovsky}. History is also a common source of leakage: if features accidentally use information from the future, offline results look better than anything achievable in practice {kaufman}. The project was motivated by the wish to test the value of history carefully, with strict time ordering, rather than to assume it.

## 1.3 Problem Statement
Fraud analysts need a tool that helps them prioritise and document suspicious transactions, while students and researchers need evidence about which modelling choices actually help on imbalanced, time-ordered data. Existing open demonstrations usually either show a polished dashboard driven by an opaque or invented score, or show offline notebook results that are never connected to a usable interface and are often evaluated with random rather than chronological splits.

The problem addressed by LayerNet is therefore: *to build an accessible, transparent fraud-investigation web prototype whose every displayed score is traceable to a stated method, and to complement it with reproducible offline experiments that evaluate trained models and recipient-history features under chronological, leakage-aware protocols, reporting results with their uncertainty and limits.*

## 1.7 Nature of the Project
LayerNet is a **development project with a research component**. The development part is a complete web application with a defined user interface, application logic, persistence, two server routes and automated tests. The research part is a set of reproducible offline experiments whose configurations, data splits, thresholds and metrics are recorded in machine-readable manifests. The project is a research prototype, not a production system. It does not make automatic decisions about real customers, and every score it shows is labelled with its method and meaning.

### 2.2.1 Financial Transactions
A financial transaction records that an amount of money moved at a certain time, through a certain channel, between two parties. Typical fields are an identifier, a timestamp, an amount, a transaction type (purchase, refund, withdrawal or transfer), the channel (web, mobile app or point of sale), a location and a device. In LayerNet the `TransactionRecord` type holds exactly these fields; account, device and location fields are optional because many inputs do not provide them. Public research datasets differ: the ULB dataset publishes only the elapsed time, the amount and 28 anonymised principal-component features V1–V28 {dalpozzolo15}, while PaySim publishes a simulated step (hour), a type, an amount and origin and destination identifiers {paysim}.

### 2.2.2 Fraud Detection
Fraud detection is the task of identifying transactions that are unauthorised or deceptive, usually so that they can be blocked or reviewed. Bolton and Hand describe it as a statistical problem with special features: classes are very unequal, labels arrive late and are sometimes wrong, and fraudsters change behaviour in response to controls {bolton}. In practice detection is usually organised as a pipeline in which automatic rules and models rank transactions and human investigators examine the highest-ranked alerts {dalpozzolo14}. Figure 2.1 shows the main families of approaches.

!FIG diagrams/out/fig2_1_taxonomy.png|6.3|Taxonomy of transaction fraud-detection approaches

### 2.2.3 Transaction Features
Raw fields are rarely used directly. Amounts are commonly log-transformed, timestamps are converted into hour of day or cyclic sine and cosine features, and categories are encoded. Bahnsen et al. showed that features describing a customer's spending pattern, such as aggregates over time windows and periodic time features, change detection results considerably on real card data {bahnsen}. LayerNet's `featureEngineering` module computes a versioned feature set (schema `layernet.transaction-features.v1`) that includes `log1p(amount)`, UTC hour with its sine and cosine, day of week, minutes since the previous transaction of the same account, counts and sums over the previous hour and day, and flags for a change of location, channel or device. In the current release these features are displayed as context and are **not used** by the score.

### 2.2.4 Historical Recipient Behaviour
Historical behaviour summarises what an entity did before the current transaction. Whitrow et al. proposed aggregating a card's earlier transactions over a window and found that aggregation helps in many, though not all, settings {whitrow}. Jurgovsky et al. treated a card's transaction sequence as input to a recurrent network {jurgovsky}. In the PaySim research track LayerNet studies the **recipient** side: for a transaction received by a customer account R at hourly step t, the history consists of earlier transactions received by R at steps strictly smaller than t, grouped into step buckets and capped at the 17 most recent buckets. Figure 2.2 illustrates this as-of construction.

!FIG diagrams/out/fig2_2_asof.png|6.3|As-of recipient history window used in the PaySim experiments

### 2.2.5 Class Imbalance
Fraud is rare. The ULB dataset contains 492 fraud cases in 284,807 transactions, about 0.17 % {ulbkaggle}, and the PaySim data used here contain 8,213 fraud labels in 6,362,620 rows. With such ratios a classifier that predicts "legitimate" for every record has an accuracy above 99 % while detecting nothing. Common responses are class weighting, under-sampling, synthetic over-sampling such as SMOTE, which creates new minority examples by interpolating between neighbouring fraud cases {chawla}, and choosing evaluation metrics that focus on the positive class. Dal Pozzolo et al. showed that under-sampling also distorts predicted probabilities, so scores must be re-calibrated before being read as probabilities {dalpozzolo15}. LayerNet uses training-only class weights and makes no probability claims.

### 2.2.6 Machine-Learning Approaches
Table 2.2 summarises the model families used or discussed in this project.

!TABLE Machine-learning approaches relevant to LayerNet
!WIDTHS 1.5,2.7,2.3
| Approach | Principle | Role in LayerNet |
| Logistic regression (SGD) | Linear model trained by stochastic gradient descent | Current-only and history arms of the PaySim ablation |
| Random Forest {breiman} | Many decision trees on bootstrap samples with random feature subsets; votes are averaged | ULB benchmark model; used in the Benchmark page |
| XGBoost {xgboost} | Gradient-boosted trees with regularisation and efficient split finding | ULB benchmark model; used in the Benchmark page |

The Python experiments use scikit-learn for the linear, Random Forest and Isolation Forest models and for metrics {sklearn}, the XGBoost library for boosting {xgboost}, and PyTorch for the Transformer.

### 2.2.7 Temporal Leakage
Leakage is the use, during training or evaluation, of information that would not be available when the prediction is made {kaufman}. In transaction data the most common forms are random train/test splits that let a model learn from the future, and history features that include the current or later transactions. Both inflate offline results. LayerNet guards against them in three ways: chronological splits (ULB by elapsed time; PaySim by whole hourly steps), history built only from strictly earlier steps with same-step transactions excluded, and thresholds chosen on validation data and then frozen before test scoring.

### 2.2.8 Evaluation Metrics
With rare positives, the precision-recall view is more informative than the ROC view {saito}. Davis and Goadrich showed that the two are related but that optimising ROC area does not guarantee good precision-recall area {davis}. LayerNet therefore reports three ranking metrics separately: **PR-AUC** (trapezoidal area under the precision-recall curve), **Average Precision** (a stepwise precision-recall summary) and **ROC-AUC**. Thresholded metrics (precision, recall, F1 and the confusion counts TP, TN, FP and FN) are reported at a threshold selected on the validation split. None of these scores is a calibrated probability.

### 2.2.9 Concept Drift
Concept drift is a change over time in the relationship between the inputs and the target. Gama et al. describe it as a change in the joint distribution of features and labels, survey how learning systems detect and adapt to it, and recommend evaluating such systems in time order {gama}. Fraud is a typical case, because fraudsters change tactics in response to controls and legitimate customer behaviour also shifts {bolton}. LayerNet does not adapt to drift. It only respects time order in evaluation: every model is trained on earlier data and tested on later data, so the reported results include whatever change happened between the two periods.

### 2.2.10 Explainability
Analysts need to know why a case was raised. Model-agnostic methods explain a single prediction after the fact: LIME fits a simple, interpretable model around the prediction using perturbed copies of the input {ribeiro}, and SHAP attributes the prediction to the input features using Shapley values from cooperative game theory {lundberg}. LayerNet takes a simpler route for its live score: the rules baseline is additive, so its explanation is exact and is shown as the list of points each rule contributed. Post-hoc explanations of the trained models are not part of the current release.

### 2.2.11 Probability Calibration
A score is calibrated when, among all cases that receive a score of p, a fraction p are positive. Niculescu-Mizil and Caruana showed that several popular learners, including boosted trees, produce poorly calibrated scores and that Platt scaling or isotonic regression can correct them {niculescu}. Guo et al. found that modern neural networks are often over-confident and that a single temperature parameter fitted on validation data is an effective correction {guo}. Under-sampling adds a further distortion {dalpozzolo15}. Because LayerNet does not calibrate any of its scores, the interface and this report describe them as priority scores, not probabilities.

## 2.3 Existing Studies and Systems
**Statistical fraud detection review.** Bolton and Hand reviewed statistical tools for fraud detection in credit cards, telecommunications, money laundering and medical claims {bolton}. They separated supervised methods, which need labelled fraud, from unsupervised methods, which flag departures from normal behaviour, and stressed that fraud detection is a moving target. Their review frames LayerNet's decision to provide both a transparent baseline and learned models.

**Fraud detection system survey.** Abdallah, Maarof and Zainal surveyed fraud detection systems across application areas and listed recurring obstacles: concept drift, support for real-time detection, skewed class distribution and the large volume of data {abdallah}. These obstacles appear in LayerNet's requirements as the chronological evaluation, the imbalance-aware metrics and the explicit scope limits.

**Practitioner lessons on card fraud.** Dal Pozzolo et al. analysed a large real card dataset from an industrial partner and discussed three practical problems: class imbalance, non-stationarity and how to assess models realistically {dalpozzolo14}. Their emphasis on realistic, time-aware assessment is reflected in the chronological splits used in LayerNet.

**ULB/Worldline dataset and calibration.** Dal Pozzolo, Caelen, Johnson and Bontempi studied how under-sampling changes the posterior probabilities of a classifier and how to correct them {dalpozzolo15}. Their work is associated with the public ULB/Worldline credit-card dataset released through the ULB Machine Learning Group {ulbkaggle}. LayerNet uses that dataset for its supervised benchmark and, following their point, describes all its model scores as uncalibrated.

**Transaction aggregation.** Whitrow et al. proposed a framework that condenses a card's transaction history into aggregated features before classification, compared it with single-transaction detection on two real datasets, and found that the aggregation window strongly affects results {whitrow}. This is the conceptual basis for the history features in LayerNet.

**Feature engineering strategies.** Correa Bahnsen et al. extended transaction aggregation with periodic features based on the time of day of earlier transactions, and evaluated several models on data from a European card processor {bahnsen}. LayerNet's cyclic hour features follow the same idea.

**Sequence classification.** Jurgovsky et al. framed card fraud detection as sequence classification with Long Short-Term Memory networks and compared it with a Random Forest using aggregated features; the sequence learner helped mainly for offline transactions {jurgovsky}. Their result motivates LayerNet's temporal experiment, which uses a Transformer encoder {vaswani} instead of a recurrent network.

**Tree ensembles and anomaly detection.** Random Forests {breiman} and gradient-boosted trees such as XGBoost {xgboost} are strong baselines for tabular data and are widely used on fraud datasets. Isolation Forest isolates anomalies with random partitioning and needs no labels {iforest}. LayerNet evaluates all three on the same ULB chronological split.

**Realistic modelling of detection systems.** Dal Pozzolo, Boracchi, Caelen, Alippi and Bontempi modelled a fraud detection system as it works in practice: investigators can check only a limited number of alerts, and their feedback arrives sooner than the labels of the remaining transactions {dalpozzolo18}. They proposed training separate models on the feedback and on the delayed labels and combining them, and evaluated alert precision rather than overall accuracy. Their framing supports LayerNet's view of the score as a way to order a limited review queue.

**Hybrid unsupervised and supervised learning.** Carcillo et al. added outlier scores computed by unsupervised methods as extra features for a supervised classifier on real card data, and reported that this can improve detection {carcillo}. LayerNet's ULB ensemble, which combines Isolation Forest with the two supervised models, explores a related idea at the score level.

**Graph-based detection.** Weber et al. released a labelled graph of Bitcoin transactions and compared classical models with graph convolutional networks for detecting illicit transactions; Random Forest with node features remained a strong baseline {weber}. Liu et al. addressed class imbalance in graph-based fraud detection with PC-GNN, which samples labels and neighbours so that the minority class is better represented, and evaluated it on public review-fraud graphs {liu21}. LayerNet does not build a transaction graph, but its recipient history is a one-hop view of the graph around each recipient account.

**PaySim simulator.** Lopez-Rojas, Elmir and Axelsson introduced PaySim, a simulator that generates mobile-money transactions from aggregated real data, to address the shortage of public data in that domain {paysim}. A public version of the generated data is distributed on Kaggle {paysimkaggle}. LayerNet uses it as a synthetic test bed for recipient history and does not treat its results as evidence about real banks.

**Commercial and open systems.** Commercial fraud platforms are widely deployed by banks and payment processors, but their models, features and evaluation are proprietary and cannot be inspected or cited reliably. Open-source projects on public code-hosting sites commonly pair the ULB dataset with a notebook or a simple dashboard. They are useful for learning, but their evaluation details vary and are often not documented; for that reason this report does not rank itself against them.

## 2.5 Summary
This chapter defined the constructs behind LayerNet and reviewed the studies it builds on. The literature agrees that fraud data are highly imbalanced and change over time, that transaction history can help, that graph structure can carry signal, that explanations and calibration are needed before scores are trusted, and that evaluation must respect time order. LayerNet responds with a transparent rules baseline in a working interface, tree-based models evaluated on a chronological ULB split, and a leakage-aware study of recipient history on PaySim. The next chapter turns these ideas into concrete requirements.

## 3.1 Introduction
This chapter specifies what LayerNet must do and the conditions under which it must do it. The requirements follow the structure recommended by ISO/IEC/IEEE 29148 for requirements engineering {iso29148}: interface requirements, functional requirements, use cases, non-functional requirements and resource, data and feasibility considerations. Each requirement has an identifier so that it can be traced to the design in Chapter 4. Requirements that are not implemented in the current release are marked as such. The full traceability of each requirement to source files and tests is given in Appendix – I.

The requirements were written for four stakeholder groups:
- **Analyst (primary user).** Enters and reviews transactions. Assumed to be familiar with web applications and with basic fraud concepts, but not with the code or the models.
- **Researcher.** Runs the offline Python pipeline from the command line and reads its manifests and reports.
- **Supervisor and evaluators.** Review the prototype, the evidence and this report.
- **External service provider.** Google, which supplies the Gemini API used by the optional assistant.

## 3.9 Project Feasibility
### 3.9.1 Technical Feasibility
All components use mature, documented open-source tools. The web application builds successfully with 13 routes, and the trained models load and score uploaded rows on an ordinary laptop without a GPU. The heaviest experiment, the PaySim ablation, took about ten minutes of training per seed and under 0.5 GB of working memory. The project is therefore technically feasible with the available equipment.

### 3.9.2 Operational Feasibility
The interface follows familiar dashboard patterns: a sidebar, page headings, forms with inline errors, tables and drawers. Every score explains itself, so an analyst does not need to know the underlying code. Because the prototype stores data in one browser and has no accounts, it is operationally suited to demonstration, teaching and research, not to use by a bank team.

### 3.9.3 Economic Feasibility
The project used free software and public datasets, and required no hosting. The only potential cost is the optional Gemini API under a paid plan. The project is economically feasible.

### 3.9.4 Legal and Ethical Feasibility
Both datasets are public research datasets. ULB features are anonymised by principal component analysis, and PaySim is synthetic, so no personal data of real customers is processed. The application never sends saved records to the assistant. Because a wrongly flagged transaction can harm a customer, LayerNet does not make automatic decisions: its scores are labelled as review priorities, not verdicts, and the scope excludes use on real customers.

## 4.3 Design Approach
LayerNet used a **top-down, modular design approach**. The system was first divided into the presentation, application logic and persistence layers, then each layer into modules with one responsibility each, and finally each module into typed functions and components. Three reasons led to this choice. First, the requirements were known at the level of pages and workflows before the details of features and metrics were settled, which fits a top-down decomposition. Second, the most important design constraint, that live scoring must remain separate from trained models, is a decision about module boundaries and is easiest to enforce from the top. Third, the repository interface allows the storage implementation to change from localStorage to a server database without changing the pages or the scoring logic.

The alternative, a bottom-up approach, starts from small reusable parts and composes them into larger ones. It was used in a limited way for the shared interface components, such as the cards, badges and charts, which were built and tried in the Component Lab before the pages used them. For the system as a whole, top-down design was preferred because it fixed the boundary between live scoring and trained models first.

Within this structure the code uses object-oriented ideas where they help, such as the `TransactionService` class with an injected `TransactionRepository`, and plain functional modules elsewhere, such as the scoring and feature functions, which are pure functions of their inputs and therefore easy to test.

This chapter described the design of LayerNet: a layered Next.js application whose live scoring is a transparent rules baseline, a separate benchmark path for the trained ULB models, and an offline research pipeline whose recorded results are summarised in Tables 4.2 and 4.3. The interface was shown through screenshots of the implemented system, and the architecture was described through the 4+1 views and a logical data model. The design meets the requirements of Chapter 3 while keeping clear limits: single-user local storage, no authentication, no cloud deployment, and no trained model in the live score.
