@CHAPTER 1|INTRODUCTION

## 1.1 Introduction
Digital payments have become part of ordinary life, and card payments, mobile wallets, online banking and point-of-sale terminals now move a very large number of small transactions every day. Each of these channels can be abused through stolen card details, account takeover, mule accounts or transfers that are later reversed, and such abuse appears in transaction data as records that look almost normal. Fraud analysts therefore face two related problems: finding the few suspicious records among very many legitimate ones, and explaining why a record deserves attention so that a human can act on it {bolton} {abdallah}. A useful tool must support both tasks and must be honest about the evidence behind every score it shows.

LayerNet addresses this problem from two directions. The first is a working web application, the **LayerNet investigation dashboard**, built with Next.js, React and TypeScript {nextjs} {react}, in which an analyst enters a transaction, receives a transparent priority score from a rules-based baseline, sees every point that contributed to it and reviews saved records later. The second is an **offline machine-learning research track** in Python that evaluates tree-based models on the public ULB/Worldline credit-card dataset {dalpozzolo15} {ulbkaggle} and studies recipient history on the synthetic PaySim dataset {paysim}. The two parts are kept separate by design: the live score comes only from the rules baseline, and trained XGBoost and Random Forest models are exposed only through a clearly labeled Benchmark page.

## 1.2 Motivation
Three observations motivated the project. First, many student and tutorial fraud-detection projects report a single accuracy figure on a highly imbalanced dataset, although accuracy is dominated by the legitimate class when fraud is well below one percent of all transactions {saito} {davis}. Second, a model score alone is rarely enough for an investigator, who needs to see which inputs pushed a case upward, what the system cannot see and what a sensible next action is. Third, history matters in fraud: aggregating a customer's past transactions can improve detection {whitrow} {bahnsen} and sequence models can learn from transaction order {jurgovsky}, but history is also a common source of leakage that makes offline results look better than anything achievable in practice {kaufman}. The project was motivated by the wish to test the value of history carefully rather than assume it.

## 1.3 Problem Statement
Fraud analysts need a tool that helps them prioritize and document suspicious transactions, while students and researchers need evidence about which modelling choices actually help on imbalanced, time-ordered data. Existing open demonstrations usually show either a polished dashboard driven by an opaque score, or notebook results that are never connected to a usable interface and are often evaluated with random rather than chronological splits. The problem addressed by LayerNet therefore has two parts. The first is *to build an accessible, transparent fraud-investigation web prototype in which every displayed score can be traced to a stated method.* The second is *to support it with reproducible offline experiments that evaluate trained models and recipient-history features under chronological, leakage-aware protocols and report their results with uncertainty and limits.*

The scope was fixed by what could be built, verified and documented within the project period, and Table 1.2 states what lies inside and outside the current release. ## 1.7 Nature of the Project
LayerNet is a **development project with a research component**. The development part is a complete web application with a defined user interface, application logic, persistence, two server routes and automated tests. The research part is a set of reproducible offline experiments whose configurations, data splits, thresholds and metrics are recorded in machine-readable manifests. The project is a research prototype rather than a production system: it makes no automatic decisions about real customers, and every score it shows is labeled with its method and meaning.

@CHAPTER 2|BACKGROUND AND EXISTING WORK

## 2.1 Introduction
This chapter provides the background needed to understand LayerNet. Section 2.2 defines the main constructs: financial transactions, fraud detection, transaction features and history, class imbalance and evaluation metrics, machine-learning approaches, temporal leakage and concept drift, and explainability and calibration. Section 2.3 reviews existing studies, systems and datasets. Section 2.4 compares the most relevant studies with LayerNet and states the research gap, and Section 2.5 summarizes the chapter.

## 2.2 Important Constructs
### 2.2.1 Financial Transactions
A financial transaction records that an amount of money moved at a certain time, through a certain channel, between two parties. Typical fields are an identifier, a timestamp, an amount, a transaction type, the channel, a location and a device. In LayerNet the `TransactionRecord` type holds these fields, with transaction types Purchase, Refund and Withdrawal and channels Web, Mobile and POS; account, device and location identifiers are optional because many inputs do not provide them. Public research datasets differ from this form. The ULB dataset publishes only the elapsed time, the amount and 28 anonymized principal-component features V1–V28 {dalpozzolo15}, while PaySim publishes a simulated hourly step, a type, an amount and origin and destination identifiers {paysim}.

### 2.2.2 Fraud Detection
Fraud detection is the task of identifying transactions that are unauthorized or deceptive, usually so that they can be blocked or reviewed. Bolton and Hand describe it as a statistical problem with special features: classes are very unequal, labels arrive late and are sometimes wrong, and fraudsters change their behavior in response to controls {bolton}. In practice, detection is organized as a pipeline in which automatic rules and models rank transactions and human investigators examine the highest-ranked alerts {dalpozzolo14}. Figure 2.1 shows the main families of approaches, from fixed rules and supervised learning to anomaly detection, sequence models and hybrid systems.

!FIG diagrams/out/fig2_1_taxonomy.png|4.2|Taxonomy of transaction fraud-detection approaches

### 2.2.3 Transaction Features and History
Raw fields are rarely used directly: amounts are log-transformed, timestamps become the hour of day or its sine and cosine, and categories are encoded. Bahnsen et al. showed that features describing a customer's spending pattern change detection results considerably on real card data {bahnsen}, and Whitrow et al. found that aggregating a card's earlier transactions helps in many, though not all, settings {whitrow}. LayerNet's `featureEngineering` module computes a versioned feature set that includes `log1p(amount)`, the UTC hour, counts and sums over the previous hour and day, and change flags, but in the current release these features are displayed as context only. In the PaySim research track, the history of a recipient account <i>R</i> at step <i>t</i> consists of earlier transactions received by <i>R</i> at strictly smaller steps, capped at the 17 most recent step buckets, as Figure 2.2 illustrates.

!FIG diagrams/out/fig2_2_asof.png|4.0|As-of recipient history window used in the PaySim experiments

### 2.2.4 Class Imbalance and Evaluation Metrics
Fraud is rare. The ULB dataset contains 492 fraud cases in 284,807 transactions, about 0.17 % {ulbkaggle}, so a classifier that labels every record as legitimate reaches an accuracy above 99 % while detecting nothing. Common responses are class weighting, under-sampling and synthetic over-sampling such as SMOTE {chawla}, together with metrics that focus on the positive class. With rare positives, the precision-recall view is more informative than the ROC view {saito}, and optimizing ROC area does not guarantee a good precision-recall area {davis}. LayerNet therefore uses training-only class weights and reports PR-AUC, Average Precision and ROC-AUC separately, with precision, recall, F1 and confusion counts at a threshold selected on the validation split.

### 2.2.5 Machine-Learning Approaches
The project uses or discusses five model families. A Random Forest averages the votes of many decision trees trained on bootstrap samples {breiman}, and XGBoost builds regularized gradient-boosted trees {xgboost}; both are used in the ULB benchmark and served by the Benchmark page. Isolation Forest is an unsupervised method that isolates anomalies with fewer random splits {iforest}, and a weighted ensemble combines it with the two supervised models. Logistic regression trained by stochastic gradient descent forms both arms of the PaySim history ablation, and a one-layer Transformer encoder, which applies self-attention to a sequence of tokens {vaswani}, is used in the PaySim temporal experiment. The experiments rely on scikit-learn {sklearn}, the XGBoost library and PyTorch.

### 2.2.6 Temporal Leakage and Concept Drift
Leakage is the use, during training or evaluation, of information that would not be available when the prediction is made {kaufman}. In transaction data its most common forms are random train-test splits, which let a model learn from the future, and history features that include the current or later transactions. A related problem is concept drift, a change over time in the relationship between inputs and labels, which Gama et al. recommend handling by evaluating learning systems in time order {gama}. LayerNet does not adapt to drift, but it guards against leakage with chronological splits, history built only from strictly earlier steps, and thresholds chosen on validation data and frozen before test scoring, so its reported results include any change between the training and test periods.

### 2.2.7 Explainability and Calibration
Analysts need to know why a case was raised. LIME explains a single prediction with a simple local model fitted on perturbed copies of the input {ribeiro}, and SHAP attributes a prediction to the input features using Shapley values {lundberg}. LayerNet takes a simpler route for its live score: the rules baseline is additive, so its explanation is exact and is shown as the points contributed by each rule. A score is calibrated when, among all cases that receive a score p, a fraction p are positive. Boosted trees and modern neural networks are often poorly calibrated and need corrections such as Platt scaling, isotonic regression or temperature scaling {niculescu} {guo}. Because LayerNet calibrates none of its scores, they are always described as priorities, not probabilities.

## 2.3 Existing Studies and Systems
Bolton and Hand reviewed statistical methods for detecting fraud in credit card, telecommunication, money-laundering and medical-claim data {bolton}. They separated supervised methods, which need labeled fraud, from unsupervised methods, which flag departures from normal behavior. Abdallah, Maarof and Zainal surveyed fraud detection systems and listed recurring obstacles such as concept drift, real-time support, skewed classes and large data volumes {abdallah}. Dal Pozzolo et al. analyzed a large real card dataset from an industrial partner and stressed class imbalance, non-stationarity and realistic assessment {dalpozzolo14}. These reviews shaped LayerNet's chronological evaluation, its imbalance-aware metrics and its explicit scope limits.

Several studies examine how transaction history should be represented. Whitrow et al. condensed a card's history into aggregated features and found that the aggregation window strongly affects results {whitrow}. Correa Bahnsen et al. added periodic features based on the time of day of earlier transactions {bahnsen}, an idea followed by LayerNet's cyclic hour features. Jurgovsky et al. treated card fraud detection as sequence classification with Long Short-Term Memory networks and found that the sequence learner helped mainly for offline transactions {jurgovsky}. Their result motivates LayerNet's temporal experiment, which uses a Transformer encoder {vaswani} instead of a recurrent network.

Other work models the detection system as it operates in practice. Dal Pozzolo et al. noted that investigators can check only a limited number of alerts and that their feedback arrives sooner than the remaining labels, and they evaluated alert precision rather than accuracy {dalpozzolo18}; this supports LayerNet's view of the score as an order for a review queue. Carcillo et al. used unsupervised outlier scores as extra features for a supervised classifier {carcillo}, an idea that LayerNet's ULB ensemble explores at the score level. Dal Pozzolo, Caelen, Johnson and Bontempi showed that under-sampling distorts predicted probabilities {dalpozzolo15}, and their public ULB/Worldline dataset {ulbkaggle} is the basis of LayerNet's supervised benchmark.

Graph-based and simulated data offer further views. Weber et al. released a labeled Bitcoin transaction graph and found that a Random Forest with node features remained a strong baseline against graph convolutional networks {weber}. Liu et al. addressed class imbalance in graph-based fraud detection with PC-GNN, which samples labels and neighbors so that the minority class is better represented {liu21}. Lopez-Rojas, Elmir and Axelsson introduced PaySim, which generates mobile-money transactions from aggregated real data {paysim} and is distributed publicly {paysimkaggle}. LayerNet's recipient history is a one-hop view of such a transaction graph, and PaySim serves only as a synthetic test bed.

Commercial fraud platforms are widely deployed by banks and payment processors, but their models, features and evaluation are proprietary and cannot be inspected or cited reliably. Open-source projects on public code-hosting sites commonly pair the ULB dataset with a notebook or a simple dashboard. They are useful for learning, but their evaluation details vary and are often undocumented, so this report compares LayerNet only with published studies whose methods are stated openly.

## 2.4 Comparison of Existing Systems
Table 2.1 compares the most relevant studies with LayerNet. It shows that history and time-aware evaluation matter, but most studies rely on private data and none provides an investigator interface that keeps the origin of each score visible. LayerNet addresses these gaps in four ways: every score is labeled with its method, meaning and limitations; the data are split chronologically and thresholds are chosen on validation data only; the value of history is isolated in a pre-registered ablation over three seeds; and the trained models are confined to a labeled Benchmark page with integrity-checked artifacts.

## 2.5 Summary
This chapter defined the constructs behind LayerNet and reviewed the studies on which it builds. The literature agrees that fraud data are imbalanced and change over time, that history and graph structure can carry signal, that scores need explanation and calibration before they are trusted, and that evaluation must respect time order. LayerNet responds with a transparent rules baseline in a working interface, tree-based models evaluated on a chronological ULB split, and a leakage-aware study of recipient history on PaySim, which the next chapter turns into concrete requirements.

## 3.8 Database Requirements
LayerNet does not use a database server. The web application keeps its data in the browser's localStorage under two keys: `layernet-transactions` holds a JSON array of analyzed transactions identified by Transaction ID, each with its score, risk band and status, and `layernet-settings` holds the theme, which is validated before it is saved. The research pipeline keeps its data as files: model artifacts with manifests in `ml/artifacts`, which are read-only at run time, and datasets in `ml/data`, which are checked against recorded hashes and excluded from version control. Because localStorage belongs to one browser profile, records are not shared between users or devices and are lost when browser data are cleared, so a server-side database with an audit trail is listed as future work.

## 3.9 Project Feasibility
### 3.9.1 Technical Feasibility
All components use mature, documented open-source tools. The web application builds successfully with 13 routes, and the trained models load and score uploaded rows on an ordinary laptop without a graphics processor. The heaviest experiment, the PaySim history ablation, took about ten minutes of training per seed and less than 0.5 GB of working memory. The project is therefore technically feasible with the equipment that was available to the team.

### 3.9.2 Operational Feasibility
The interface follows familiar dashboard patterns: a sidebar, page headings, forms with inline errors, tables and drawers. Every score explains itself, so an analyst does not need to understand the underlying code to use it. Because the prototype stores data in one browser and has no user accounts, it is operationally suited to demonstration, teaching and research, but not to daily use by a bank's fraud team.

### 3.9.3 Economic Feasibility
The project used only free software and public datasets, and it required no hosting, licenses or special hardware. The only possible cost is the optional Gemini API when it is used under a paid plan, and the application works without it, because every other feature runs locally. Future costs, such as cloud hosting or a managed database, would arise only if the prototype were deployed for several users. The project is therefore economically feasible within the resources of a student team.

### 3.9.4 Legal and Ethical Feasibility
Both datasets are public research datasets: the ULB features are anonymized by principal component analysis, and PaySim is synthetic, so no personal data of real customers are processed. The application never sends saved records to the assistant. Because a wrongly flagged transaction can harm a customer, LayerNet makes no automatic decisions; its scores are labeled as review priorities rather than verdicts, and use on real customers is outside its scope.

## 3.10 Summary
This chapter specified twelve functional requirements for the web application, seven for the research pipeline, eight use cases, eight non-functional requirements, and the hardware, software, resource and data requirements of the project. The feasibility analysis showed that LayerNet can be built and run with free tools on one computer, without processing personal data. Chapter 4 describes the design that satisfies these requirements and shows the implemented interface.

The application follows the layered architecture shown in Figure 4.2. The presentation layer contains the pages and shared components, such as the application shell and the history table. The application logic layer contains the transaction service, the rules baseline, feature engineering and metrics, all written as typed TypeScript modules. Rules baseline v1 adds log-scaled amount points (at most 50) and fixed points for type, channel and UTC night-time hours, clamps the sum to 0–100, assigns risk High at 80 or more and Medium at 40 or more, and decides Block at 85 or more and Review at 60 or more. The persistence and server layer contains the localStorage repository, the chat route, limited to 30 s, and the benchmark route, which runs the Python replay in a child process with a 120 s timeout.

!FIG diagrams/out/fig4_2_layers.png|3.9|Layered architecture of the LayerNet web application

The offline research pipeline, shown in Figure 4.3, is a separate part of the system that is run from the command line. Track A prepares the ULB data, splits them chronologically, trains the supervised and unsupervised models, selects thresholds on validation data and writes a manifest for each model. Track B builds as-of recipient histories from PaySim and runs the temporal experiment and the history ablation. The only connection between the pipeline and the web application is the pair of saved ULB model artifacts that the Benchmark page replays.

## 4.3 Design Approach
LayerNet used a **top-down, modular design approach**. The system was first divided into the presentation, application logic and persistence layers, then each layer into modules with one responsibility, and finally each module into typed functions and components. This approach fitted the project because the requirements were known at the level of pages and workflows before the details of features and metrics were settled. It also made the most important constraint, that live scoring must remain separate from trained models, a decision about module boundaries that could be enforced from the start. Finally, the repository interface allows the storage to change from localStorage to a server database without changing the pages or the scoring logic.

The alternative, a bottom-up approach, starts from small reusable parts and composes them into larger ones. It was used in a limited way for the shared interface components, such as cards, badges and charts, which were built and tried in the Component Lab before the pages used them. Within the top-down structure, the code uses object-oriented ideas where they help, such as the `TransactionService` class with an injected `TransactionRepository`, and pure functional modules elsewhere, such as the scoring and feature functions, which are easy to test because they depend only on their inputs.

## 4.4 Interface Design
The interface was designed around the analyst's workflow: analyze a transaction, see why it scored as it did, and review saved records later. Its design principles are consistency, with one shell, one card style and one table style; honesty, because every score shows its method and meaning; accessibility, through labels, focus order, visible focus and keyboard support; and responsiveness, with a sidebar on large screens and a drawer on small ones. The application has eight screens, one for each use case: Dashboard, Analysis, History, Analytics, Benchmark, Settings, Health and the assistant panel.

## 4.5 4+1 View Model
Kruchten's 4+1 view model describes a software architecture through four views, which are tied together by a set of scenarios {kruchten}. For LayerNet, the logical view shows the domain types and their relationships in a class diagram, and the process view shows the run-time behavior in an activity diagram and two sequence diagrams. The development view shows the organization of the code in a component diagram, and the physical view maps the software onto hardware in a deployment diagram. The scenarios are the use cases of Chapter 3, in particular UC-01 and UC-05, which are traced through all four views in Section 4.5.5.

### 4.5.1 Logical View
Figure 4.8 shows the class diagram. TypeScript types are drawn as UML classes, interfaces are marked «interface», and modules of pure functions are marked «module»; only the attributes and operations needed to explain the design are shown. `Transaction` extends `TransactionRecord` with the score, risk and status. `TransactionService` aggregates a `TransactionRepository`, uses the scoring and feature modules, and creates an `AnalysisResult`, which is composed of `TransactionFeatures` and a `BehavioralBaseline`. The localStorage repository is one implementation of the repository interface.

!FIG diagrams/out/fig4_10_class.png|4.9|Class diagram of the LayerNet domain and services

### 4.5.2 Process View
Figure 4.9 is the activity diagram of the main workflow, analyzing a transaction. The workflow has two decision points: input validation, which returns the analyst to the form with field errors, and saving, which either shows the result and a confirmation or shows an error. Between them, the system loads earlier records, computes features and the account baseline for display only, and applies the rules baseline. The amount contributes min(50, floor(10 · log10(max(1, amount)))) points, and type, channel and night-time hours then add or subtract fixed points, so the result can always show the exact reason for every score.

!FIG diagrams/out/fig4_11_activity.png|3.0|Activity diagram: analyze transaction

Figures 4.10 and 4.11 are the sequence diagrams of the two most important interactions. In the first, analyzing and saving a transaction, all messages pass between objects inside the browser: the page calls the transaction service, which reads earlier records from the repository, computes features, applies the rules baseline and saves the result, and no server call is involved. In the second, the benchmark replay, the page sends the uploaded file to the Node.js route, which starts the Python process and exchanges data with it through standard input and output. Every model file is checked against its manifest hash before it is loaded, and a timeout or validation error is returned to the page as a typed failure.
